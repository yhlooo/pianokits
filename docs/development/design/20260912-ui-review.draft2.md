## 2. 成立项 P0：窄屏（≤768px）布局不可用

### 实测（每次重开页面，非缓存）

| 视口     | 侧栏 | 内容区 | 瀑布流 | 琴键   | 横向溢出             |
| -------- | ---- | ------ | ------ | ------ | -------------------- |
| 1512×945 | 264  | 1248   | 600    | 600×73 | 否                   |
| 1024×768 | 264  | 760    | 356    | 356×43 | 否                   |
| 820×1180 | 264  | 556    | 524    | 524×64 | 否                   |
| 768×1024 | 264  | 504    | 472    | 472×58 | **是**               |
| 390×844  | 264  | 126    | 94     | 94×11  | **是**（溢出 406px） |

390×844 下：侧栏固定占 264px，内容区只剩 126px，琴键总高 11px；
`.stage` 的 x 坐标为 **-142**（左边缘被推出视口），文档横向可滚动 406px。

![390px 手机竖屏：内容被侧栏挤成一条，左边缘出界](images/20260912-ui-review/06-mobile-390.png)

820×1180 平板竖屏（已载入曲目）：

![820px 平板竖屏：分屏堆叠后每块高度不足](images/20260912-ui-review/07-tablet-820.png)

### 根因

全站唯一的响应式断点只把分屏改成上下堆叠，**没有处理侧栏占宽与播放坞**：

```css
@media (max-width: 900px) {
  .stage--split {
    grid-template-columns: 1fr;
    grid-template-rows: 1fr 1fr;
  }
}
```

而 `src/ui/*.ts` 里已有成熟的双模态交互（`touchMode = matchMedia('(hover: none)')`：
触控端点击展开弹层、删除按钮常显），说明"支持触屏"的意图明确，只是尺寸模型没跟上。

### 建议（若决定支持窄屏）

| 断点       | 侧栏                          | 视图                 | 播放坞                                      |
| ---------- | ----------------------------- | -------------------- | ------------------------------------------- |
| ≥1024px    | 常驻 264px（现状）            | 分屏，可收起侧栏     | 现状                                        |
| 768–1024px | 默认收起，浮层抽屉（overlay） | 默认仅瀑布，谱面可切 | 现状                                        |
| <768px     | 全屏抽屉，顶部"库"按钮唤起    | 单视图，二选一       | 精简：隐藏时间码与右侧工具组，仅留播放/停止 |

要点：侧栏改 `position: fixed` 浮层 + 遮罩，不再挤压内容区；`.content` 增加 `min-width: 0`；
播放坞左侧已有 `.transport__sidebar-toggle`，窄屏复用它作为抽屉入口。

## 3. 成立项 P2：两处局部缺陷

### 3.1 播放/停止按钮尺寸不等

实测播放/暂停 **36×36**、停止 **32×32**（`.transport__play` 显式 36px，
停止走 `.icon-btn` 默认 32px）。两者相邻并排，基线不齐：

![播放坞特写：播放 36×36 与停止 32×32 并排](images/20260912-ui-review/10-playerdock.png)

**建议**：统一为 36px；若想保留"主/次"区分，则把差异拉开到明确档位（如 40 / 32），
而不是 4px 的模糊差。

### 3.2 非 ASCII 轨名显示为乱码（可稳定复现）

**这不是浏览器问题，是解析库行为，已用可控夹具证明。**

复现步骤：

1. 用 UTF-8 编码的轨名构造 SMF（`右手旋律` / `左手伴奏`，SMF 常见写法）；
2. 导入 → 曲目正常播放、谱面正常，**库列表显示的是文件名**（所以从库列表看不出问题）；
3. 悬停播放坞的"练习"图标展开练习菜单 → 轨名显示为 `å³ææå¾` / `å·¦æä¼´å¥`。

![练习菜单：UTF-8 中文轨名显示为乱码](images/20260912-ui-review/17-cjk-track-names.png)

根因在 `@tonejs/midi`：文本事件按 **latin-1** 逐字符解码，UTF-8 字节被当成独立码点。
`src/core/midi/write.ts` 的注释已记录**写出方向**的同一限制（故导出固定用 ASCII 轨名
`PianoKits Recording`），但**读入方向**没有处理。

直接验证（用应用自身的解析器，绕开 UI）：

```js
// 在页面上下文执行
const mod = await import('/src/core/midi/parse.ts')
const buf = await (await fetch('/<utf8 轨名的>.mid')).arrayBuffer()
mod.parseMidi(new Uint8Array(buf)).tracks.map((t) => t.name)
// => ['å³ææå¾', 'å·¦æä¼´å¥']   期望 ['右手旋律', '左手伴奏']
```

复现夹具由 `scripts/ui-audit-export.mjs` 的 `makeCjkMidi()` 生成到
`.tmp/audit/cjk-tracks.mid`（手工拼 SMF 字节，不用 `@tonejs/midi` 写入——
后者写出的文件本身就是坏的，无法用来证明解析端的问题）。

**建议**：单独立项（属解析层，不属视觉层）。可选方向：
① 解析后尝试按 UTF-8 重新解码（把 latin-1 字符串还原成原始字节，用
`TextDecoder('utf-8', { fatal: true })` 校验，成功则替换）；
② 增加 GBK 回退（中文 MIDI 多来自老 DAW，实际常为 GBK）；
③ 兜底：解码失败时显示 `Track N` 而不是乱码。

## 4. 成立项 P3：字阶存在越界值

`style.css` 的字阶为 0.6875 / 0.75 / 0.8125 / 0.875 / 1 / 1.25 / 1.75 rem，
以下取值不在阶内，且集中在"读数类"元素上（彼此也未形成档位）：

| 选择器                       | 值         | 用途         | 建议                          |
| ---------------------------- | ---------- | ------------ | ----------------------------- |
| `.midi-debug__note`          | `3.5rem`   | 调试页音名   | 归入新档 `--fs-readout-lg`    |
| `.midi-debug__key`           | `3.5rem`   | 调试页琴键名 | 同上（与音名同档，合理）      |
| `.midi-debug__velocity`      | `1.5rem`   | 调试页力度   | 归入 `--fs-readout`           |
| `.midi-debug__pedal-percent` | `1.5rem`   | 调试页踏板   | 同上                          |
| `.midi-debug__pedal-raw`     | `1rem`     | 调试页原始值 | 降一档到 0.875rem（次要读数） |
| `.midi-debug__retry`         | `0.8rem`   | 重试按钮     | 改 `0.8125rem`                |
| `.recorder__timer`           | `1.375rem` | 录音计时     | 归入 `--fs-readout-lg`        |
| `.dialog__title`             | `1rem`     | 弹窗标题     | 与面板标题统一                |

**建议**：把"读数类字号"抽成独立档位（`--fs-readout` / `--fs-readout-lg`）——
等宽数字读数的视觉重量需求与正文不同，这是当前字阶唯一真正缺失的一类；
其余取值归并到最近档位，与色彩一样做到 token 化（色彩已 0 硬编码，字号还没有）。

## 6. 测量与复核方法（draft1 教训的固化）

draft1 出错的环节是"目测缩略图"。以下做法已固化，后续评估请照做：

1. **几何以 `getBoundingClientRect()` 为准，不看图**，且**每次重开页面**（避免复用上一状态的渲染）：

   ```js
   const r = await page.evaluate(() => {
     const g = (s) => {
       const e = document.querySelector(s)
       if (e === null) return null
       const b = e.getBoundingClientRect()
       return [Math.round(b.x), Math.round(b.width), Math.round(b.height)]
     }
     return {
       lib: g('.library'),
       stage: g('.stage'),
       wf: g('.waterfall'),
       score: g('.score'),
       piano: g('.piano'),
       overflowX: document.documentElement.scrollWidth - window.innerWidth,
     }
   })
   ```

2. **截图内容用像素扫描验证**，确认边界、并排除通知条等混入物：

   ```python
   # 扫描指定行，输出"亮块"区间（用于定位琴键、卡片、通知条的边界）
   runs([v > 190 for v in row], minlen=4)
   ```

另外两条本次踩到的坑，一并固化：

- **`.tmp/` 会跨天累积**，旧图与当前实现不符。配图一律由 `ui-audit-export.mjs`
  重新生成，不手工挑历史文件。
- **headless Chromium 会拒绝 MIDI 授权**，页面右下角弹出"MIDI 授权被拒绝"通知并进入截图。
  截图脚本统一用 `page.addInitScript` 注入假 MIDI 设备（见 `ui-audit-export.mjs` 的
  `FAKE_MIDI`），既消除该通知，也让"已连接 MIDI"相关 UI 可截。
