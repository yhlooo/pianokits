## 1. P0：窄屏自适应（侧栏浮层抽屉 + 播放坞精简）

### 实现

**行为**（断点 900px，与既有 `.stage--split` 堆叠断点一致）：

| 宽度   | 侧栏                              | 视图         | 播放坞                     |
| ------ | --------------------------------- | ------------ | -------------------------- |
| >900px | 常驻 264px（原行为不变）          | 分屏         | 完整                       |
| ≤900px | 浮层抽屉，默认收起                | 分屏上下堆叠 | 仅"侧栏开关 + 播放 + 停止" |
| ≤560px | 抽屉宽度 88vw，舞台内边距收到 8px | 同上         | 同上                       |

**代码**：

- `src/app.ts`：新增 `drawerMode`（`matchMedia('(max-width: 900px)')`）与 `syncSidebar()`，
  统一把「桌面折叠态 / 窄屏抽屉开合态」落到 DOM class 上；
  `toggleSidebar()`（播放坞按钮）、`collapseSidebar()`（抽屉内关闭按钮）按模式分派；
  点遮罩、按 Esc、选中曲目都会收起抽屉；跨断点时重置状态。
- `src/ui/transport-view.ts`：`setSidebarDrawerMode(active, open)` —— 抽屉模式下该按钮**常显**，
  并在"侧栏图标"与"关闭图标"之间切换。
- `src/ui/library-view.ts`：收起按钮**保持在侧栏左下角**（原有位置）；另加一个**抽屉专用关闭按钮**
  （`.library__close`，默认 `display: none`），仅抽屉打开时作为头部流内 flex 项显示，
  与导入按钮天然对齐。原因：抽屉是浮层，需要一个近在手边的关闭出口；
  而把左下角那个按钮"搬"到头部会带来定位难题——按钮在 DOM 里属于脚注，而 `.library`
  是 `position: fixed` 且带 `transform`（抽屉位移），它自身成为绝对定位的包含块，
  坐标原点在视口顶部而非侧栏，算出的位置会偏到屏幕最上方。用独立的流内按钮最省事也最稳。
- `src/style.css`：`.main.is-drawer` 把侧栏列收为 0，`.library` 改 `position: fixed` 浮层 +
  位移动画 + `.main__backdrop` 遮罩；`.transport__time` / `.transport__tools` 在窄屏隐藏。

## 2. 其余三项

### 2.1 播放/停止按钮统一 36px

`.transport__stop` 显式设为 36×36（原为 `.icon-btn` 默认 32px）。
窄屏（≤900px）两者一起放大到 44×44，作为触控热区。

### 2.2 非 ASCII 轨名乱码修复

`src/core/midi/parse.ts` 新增并导出 `decodeMidiText(raw)`：

1. 若字符串含 >U+00FF 的字符，说明它不是"逐字节解码"的产物，原样返回；
2. 否则把每个码位还原成一个字节，用 `TextDecoder('utf-8', { fatal: true })` 严格解码；
3. 解码失败 → 视为**真正的 latin-1 文本**，原样返回（不误判）；成功且与原文不同 → 用解码结果。

关键点是第 3 步的 `fatal: true`：它让 `café`（合法 latin-1，字节 `EB` 后缺续接字节）
不会被误当成 UTF-8，而 `右手旋律` 的 UTF-8 字节序列能正确还原。

`parseMidi` 的轨名映射改为 `decodeMidiText(t.name).trim()`，空名仍退到 `Track N`。

**效果**（同一夹具，修复前后）：

```
修复前：["å³ææå¾", "å·¦æä¼´å¥"]
修复后：["右手旋律", "左手伴奏"]
```

![练习菜单：中文轨名已正确显示](images/20260912-ui-review/17-cjk-track-names.png)

**测试**：`src/core/midi/parse.test.ts` 新增 6 个用例（ASCII、UTF-8 中文、UTF-8 西欧字符、
真 latin-1 不被误判、已解码含中文的原样返回、`parseMidi` 端到端含空名回退）。

**未覆盖**：GBK / Big5 等编码仍会落回乱码（零依赖下 `TextDecoder` 不可靠支持这些编码）。
如后续需要，须引入解码依赖，已记在 draft2 的待议 Q2。

### 2.3 字阶 token 化

`style.css` 的 `:root` 新增 12 个字号 token，并把**全部 39 处 `font-size` 字面量**替换为 token
（现在已无任何字面量）：

```
正文系：--fs-caption 9.6px / --fs-meta 10.5px / --fs-body 11.4px /
        --fs-body-strong 12.25px / --fs-title 14px / --fs-panel 17.5px / --fs-section 24.5px
读数系：--fs-readout-sm 19.25px / --fs-readout-md 21px /
        --fs-readout-lg 42px / --fs-readout-xl 49px
--fs-root 14px（根字号基准）
```

两点说明：

- **根字号是 14px**，故 `1rem = 14px`（不是 16px）。draft2 §4 的表格按 16px 折算过 px，
  实际渲染值以本表为准（例如"调试页音名 3.5rem"实为 49px 而非 56px）。已在新 token
  注释里写明实际 px，避免后续再算错。
- 读数系单列一档是有依据的：调试页的力度角标注释明确写了它是"音名的 0.43 倍"
  （1.5rem : 3.5rem），所以这两个值不是随手取的，而是有意的比例关系；
  谱面空状态剪影的 3rem 同理属于"展示字号"而非正文。

`0.8rem`（`.midi-debug__retry`）是唯一的笔误型越界值，已归到 `--fs-body`（0.8125rem），
渲染值 11.2px → 11.375px，属本次唯一可见的字号变化。

## 4. 修复过程中引入并已修掉的回归：宽屏侧栏收不起来

**现象**：宽屏（>900px）下点侧栏里的 × 后侧栏确实收起了，但播放坞最左的"展开侧栏"按钮
**不显示**，侧栏再也打不开。

**根因**：合并 `setSidebarCollapsed()` 与 `setSidebarDrawerMode()` 时，
把"桌面是否已收起"这个状态在调用处传丢了——传的是 `drawerMode && drawerOpen`，
桌面下恒为 `false`，而按钮可见性判断是 `active ? true : open === false`，
于是把"抽屉未打开"误读成"侧栏未收起"，按钮反而常显/常隐判断颠倒。
两个模式的"收起"含义不同（桌面 = 侧栏已收起，窄屏 = 抽屉已打开），必须按模式取对应值。

**修复**：`transportView.setSidebarState(drawer, collapsed)` 显式接收各模式下的"收起"语义，
调用处按 `drawerMode ? drawerOpen : sidebarCollapsed` 取值；方法名与参数名一并改掉，
避免再用一个含糊的 `open` 同时表示两种含义。

**为什么没被早发现**：侧栏宽度、`is-collapsed` class 都是对的，
只有"按钮可见性 ↔ 侧栏状态"这一条一致性错了——而肉眼与几何测量都只看宽度。
因此新增了 `scripts/assert-sidebar.mjs` 把这条不变式固化成断言：

```sh
pnpm dev
node scripts/assert-sidebar.mjs   # 退出码非 0 即失败
```

它断言：桌面/窄屏各自的展开按钮可见性与图标语义、遮罩与抽屉开合一致、
901/900/899 三个断点无横向溢出。**已做变异测试**：把有 bug 的取值方式注入回去，
脚本在"桌面 收起态"一例上返回 FAIL 并以退出码 1 结束，确认该断言真能拦住这个 bug。

## 4.1 调整：侧栏按钮位置回归

上一条修复后收到反馈：**收起侧栏的按钮不该挪到音乐库标题右边**，原来在侧栏左下角挺好。
已改回——桌面端 `.library__collapse` 仍在脚注左下角；抽屉的关闭出口改为头部独立的
`.library__close`（仅抽屉打开时出现）。两个按钮各司其职，不再用"一个按钮换定位"的写法。

同时把播放坞最左按钮（在播放键左边）的语义固定为：桌面=展开侧栏（仅在已收起时出现），
窄屏=音乐库开关（常显）——这也是用户认可的位置。
