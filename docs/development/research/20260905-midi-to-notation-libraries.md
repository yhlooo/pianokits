# 调研：可用 TS/JS 库实现 MIDI 转五线谱吗（复核）

- 日期：2026-09-05
- 关联参考文档：
  - `docs/development/reference/midi/rendering-libraries.md`（§2.9 为本文新增的复核数据，
    其余库数据沿用该文档，引用处标 `[ref-*]`）
  - `docs/development/research/20260905-waterfall-and-notation.md`（先前的宽口径调研，
    本文 §3 结论与之印证）
- 背景：pianokits 当前五线谱"参考谱"准确率不理想，需要确认能否换用/引入某个 TS/JS 库
  直接完成 MIDI → 五线谱，或显著改善记谱质量。

## 1. 结论摘要

| 问题                                     | 结论                                                                                                                                                                                                                                                                                                                          |
| ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 有没有"一行调用"的 MIDI→五线谱 TS/JS 库   | **没有。** 截至 2026-09-05，npm 全量检索（`midi musicxml`、`midi to sheet music`）命中的包要么弃更、要么方向不符，无一是可用的 MIDI→乐谱转换器 `[ref-2.9]`。                                                                                                                                    |
| 现有库能做什么                           | 现有生态里只有两类库：**MIDI 解析器**（`@tonejs/midi`、`midi-file` → 输出事件流，无记谱）与**雕刻引擎**（VexFlow / OSMD / abcjs / alphaTab → 吃 MusicXML/ABC/DSL，不做 MIDI 转换）`[ref-2.x]`。两者之间"MIDI→谱面"的环节至今无人补上。                                                                                |
| 准确率差是不是用错库了                   | **不是。** 准确率差的根源在自研的 `quantize.ts`（量化/分声部/拼写）本身，这是公认难解的转录（transcription）问题；换渲染库（VexFlow/OSMD/abcjs）不改变记谱内容，只会换层皮。                                                                                                                                |
| 有没有可借力的库改善准确率               | 有，但都是**算法零件**而非转换器：`@tonaljs`（音高拼写/调号/和弦上下文）、Magenta `core/sequences`（量化参考实现，库已弃更，仅借鉴算法）`[ref-2.9.5]`。真正的提升要靠改进 `quantize.ts` 的量化与分声部算法。                                                                                                   |

## 2. 库生态全景（按能力分层，数据见 [ref-2]、[ref-2.9]）

### 2.1 雕刻引擎（渲染层，不做转换）

| 库          | 输入            | 一句话定位                                   | 能否改善"准确率" |
| ----------- | --------------- | -------------------------------------------- | ---------------- |
| VexFlow（在用）| 音符对象/DSL    | 纯雕刻引擎，排版好，不做任何音乐判断         | ❌ 只换渲染层   |
| OSMD        | MusicXML        | VexFlow 之上的 MusicXML 渲染器               | ❌ 需先有 MusicXML |
| abcjs       | ABC 文本        | ABC→谱，MIDI 只是其**输出**方向              | ❌ 无 MIDI→ABC |
| alphaTab    | MusicXML/GP     | 多乐器/吉他谱渲染，带内置播放                | ❌ 无 MIDI 输入 |

### 2.2 MIDI 解析器（输入层，不做记谱）

`@tonejs/midi`（在用）、`midi-file` 等只把 .mid 字节解析成 `{pitch, start, end, velocity}`
事件流。它们给的是"何时按/松哪个键"，离谱面还差量化、分声部、拼写、时值、休止符。

### 2.3 "MIDI→MusicXML/乐谱转换器"候选（全部不可用）

| 候选                          | 现状（2026-09-05 实测）                                                        |
| ----------------------------- | ------------------------------------------------------------------------------ |
| `midi2musicxml`（kaibadash）  | **Java 11+**，非 JS；为 NEUTRINO 歌声合成服务；README 自述不再维护，指向 tyouseisientool `[ref-2.9.1]` |
| `concertmaster`               | npm 0.2.2，2018 年停发，"simple module"，无实际转换能力 `[ref-2.9.2]`           |
| `musicvis-lib`                | npm 0.55.0，2022 年，定位是分析/可视化库，非转换器 `[ref-2.9.3]`                |
| `webmscore`（LibreScore）     | **只收 mscz**（方向相反：mscz→MIDI/MusicXML），GPL、2023 停发 `[ref-2.5]`       |
| `muse-js`（npm）              | **撞名**：实为 2016 年脑电头环蓝牙库，与 MuseScore 无关 `[ref-2.9.4]`           |
| `music21j`                    | 只做 MusicXML 解析/序列化，**无 MIDI 文件导入** `[ref-2.4]`                     |
| `@sudobility/music_codecs`    | BUSL-1.1 非开放许可证，排除 `[ref-2.8]`                                        |

> 一句话：浏览器 JS 生态里，"把 .mid 直接变成能读的五线谱"这个转换器，2026-09 仍不存在。

## 4. 准确率差的真正原因与可借力的库

### 4.1 当前 `quantize.ts`（M1 "参考谱"）的已知局限

对照源码（`src/core/midi/quantize.ts`）与 `score-view.ts`：

1. **固定 1/8 网格量化**（`QUANTIZE_STEP = 0.5`）：一切不在八分音符网格上的起止都被
   四舍五入。十六分音符段落被压成八分；三连音、摇摆、自由速度（rubato）被硬掰到错误
   位置——这是"看着不对劲"的最大来源。
2. **硬编码 C4 分界**（`SPLIT_PITCH = 60`）：左右手纯按音高切，不考虑时间重叠与交叉手，
   跨 C4 的左手和弦会被劈到两个谱表。
3. **每谱表单声部**（`normalized` 段把重叠事件起点收紧）：右手"旋律 + 伴奏"两线条、
   或左手持续低音 + 走动声部会被强行压成单声部，丢失复调。
4. **无三连音/连音检测**、无附点优化。
5. **拼写只看调号**（`spellPitch`），无和声上下文/旋律走向，升降号选择偶发别扭。
6. **符杠** `Beam.generateBeams` 不做节奏分组，跨拍符杠不规则。

这些都不在"库"的层面，而在转录算法本身。

### 4.2 能借力的库（零件，非转换器）

| 库                        | 用途                             | 状态                                  |
| ------------------------- | -------------------------------- | ------------------------------------- |
| `@tonaljs/note/key/pcset` | 音高拼写候选枚举、调号估计、和弦/音阶上下文 | MIT、活跃，体积小，纯函数        |
| `@magenta/music` sequences| 量化参考实现（`quantizeNoteSequence`、`applySustainControlChanges`）| npm 2021 停发，仅借鉴算法 `[ref-2.9.5]` |

> `@tonaljs` 是唯一值得**引入为依赖**的候选：它把拼写/调号估计里最繁琐的音高理论
> 计算交给久经测试的库，量化、分声部、连音仍须自研。

### 4.3 提升准确率的路径（算法工作，非换库）

1. 自适应量化：先做拍速/拍点估计（note-on 密度 + 能量），再用更细网格（1/16）+
   最小代价吸附，而非固定 1/8。
2. 复调分声部：在"左右手"之上，每只手里再做多 voice（按音区聚类 + 重叠检测）。
3. 连音检测：3:2 / 2:3 网格试探，识别三连音等。
4. 拼写增强：用 `@tonaljs` 生成候选拼写，按调号 + 和声上下文 + 旋律走向打分。
5. 踏板：读 sustain 控制事件延长 note 结束（参考 `applySustainControlChanges` 思路）。
6. 符杠按拍/节奏分组。

## 5. 建议

1. **不做"换库"动作**：渲染层 VexFlow 已是正确选择；没有更准的转换库可换。
2. **引入 `@tonaljs`** 作为拼写/调号估计的零件（低成本、低风险、直接改善拼写别扭）。
3. **把改进目标定在 `quantize.ts`**：优先做"自适应量化 + 更细网格 + 复调分声部"
   （这是准确率提升的最大杠杆），三连音与和声拼写作为后续。
4. 若后续需要专业排版，先把自研转换器输出抽象成 MusicXML（序列化用 `musicxml-io`），
   渲染端即可切 OSMD/alphaTab；但这也只是换渲染，不改记谱准确率。
