# 调查：播放界面五线谱「绘制很乱」的成因定位

- 日期：2026-09-13
- 触发：用户反馈播放（练习）界面五线谱「绘制很乱、不正确」
- 方法：Playwright 在真实运行的应用（http://localhost:5173/midi-player）中截图 + 抽取 SVG 几何 +
  用应用自身的 `parseMidi`/`quantizeToScore` 与 VexFlow 交叉比对
- 关联实现：`src/ui/score-view.ts`、`src/core/midi/quantize.ts`

## 0. 结论速览

| 怀疑项                           | 实测结果                                                   | 是否问题          |
| -------------------------------- | ---------------------------------------------------------- | ----------------- |
| 音高 / 八度是否画错              | 与量化模型逐一比对，完全一致                               | ❌ 不是           |
| 分谱表（左右手）是否正确         | 按 MIDI 轨分组，与模型一致                                 | ❌ 不是           |
| 拍号 / 调号是否正确              | 与 MIDI 元数据一致；调号估计 sf=-2 正确                    | ❌ 不是           |
| 音名拼写 / 临时记号              | 还原记号（En/Bn）用法正确，统计无异常                      | ❌ 不是           |
| 多声部同拍点是否横向对齐         | 共享 `TickContext`，实测错位 0px                           | ❌ 不是           |
| 符头是否互相碰撞                 | 199 个位置中 4 处间距 <8px（偶发，不严重）                 | ⚠️ 轻微           |
| **谱表间距是否足够（加线越界）** | **相邻谱表内容实际重叠 17px（demo）/ 42px（6 轨）**        | ✅ **是（主因）** |
| **源数据连奏断音被拆成延音线**   | **129 处相邻同音首尾相接，本可合并为一个音**               | ✅ **是（次因）** |
| 空小节没有全小节休止符           | 无事件声部完全不画休止符，小节留白                         | ⚠️ 记谱欠规范     |
| 系统左端是否绘制大括号/方括号    | 只画了一条竖线（`singleLeft`），草案 §3 要求 brace/bracket | ⚠️ 观感           |

**「乱」的主要来源是布局，不是音高或节奏画错。** 两处硬伤：①固定谱表间距容不下加线；
②源 MIDI 的连奏断音被如实拆成「延音线粘连的碎片」。

## 1. 五线谱本身画得对（逐项验证）

用 VexFlow 的坐标公式对渲染出的符头纵坐标反查音名（标定：treble `F5=50`、`C5=65`、`C4=100`；
bass `A3=150`、`C3=175`，每个音级 5px），与 `quantizeToScore` 的输出逐音符比对：

- `demo.mid` 系统 0 高音谱表：模型 `REST C5 C5 D5 E5 | G5 REST A5 A5 G5`（A5 的两片是延音线）
  ↔ 渲染完全一致；低音谱表 `REST C3 C3 G3 E4 G4 | E4 G3 E4 G5 G5 G2 G2` 同样一致。
- 节奏、附点、符杠方向、延音线、临时记号数量均与模型匹配。

曾在排查中出现「渲染音高整体偏高一个音级」的假象，原因是**VexFlow 的符头 `text.y`
等于符头所在线/间的 y 值**（实测 `c/5 → y=65`，与 `stave.getYForLine` 同一坐标系），
早期用「音级中心 = 线之间」反推才产生偏差。这一点记录下来避免后人重复踩坑。

## 2. 主因：固定谱表间距（`STAFF_GAP = 100`）容不下加线，谱表内容互相重叠

`score-view.ts`：

```ts
const STAFF_TOP_Y = 10
const STAFF_GAP = 100 // 谱表原点间距；谱表自身高 40（5 线 × 10px）
const BOTTOM_PAD = 100
```

- 相邻谱表的**净空恒为 `100 - 40 = 60px`**（= 6 个线间距），与 `20260905-debug-tools.md:194`
  「两轨之间净空取 6 个线间距」一致。
- 但钢琴两手的实际音域经常需要 5 条以上加线。实测各谱表内容相对谱表原点的外扩量：

| 文件                   | 各谱表内容外扩（上/下）           | 需要的净空 | 当前净空 |
| ---------------------- | --------------------------------- | ---------- | -------- |
| `demo.mid`             | treble 上20 / bass **上65**       | 92px       | 60px     |
| `梦中的婚礼.mid`       | treble **上90** / bass 上55       | 107px      | 60px     |
| `pianokits-6track.mid` | treble 上90、bass 下55、bass 上10 | 102px      | 60px     |
| `multitrack.mid`       | treble 上45 / 下35 …              | 77px       | 60px     |

按「内容包围盒」精确计算相邻谱表的实际重叠：

```
demo.mid           系统0/1  treble 内容到 y=102，bass 内容起于 y=85 → 重叠 17px
pianokits-6track   系统0/1  staff#4 内容到 y=502，staff#5 起于 y=460 → 重叠 42px
梦中的婚礼.mid     无重叠（但净空仅剩 -28px，视觉上两谱表已贴在一起）
```

这就是截图里「低音谱表的高音加线一直顶进高音谱表、符干横穿另一谱表」的来源。
`demo.mid` 低音谱表有一个需要在低音谱表上画 **8 条加线** 的 G5（源文件左手轨真的是 MIDI 79），
而对应位置的高音谱表也在画加线，两者在同一像素区域叠在一起。

**修法**：谱表间距改为按本系统实际音域计算，而不是固定 100：

```
gap(i) = 40(谱表高) + max(60, 上一谱表内容下沿 + 本谱表内容上沿 + 余量(符杠/连线 ~12px))
systemHeight = STAFF_TOP_Y + Σ gap + BOTTOM_PAD
```

实测建议值：`demo 132`、`梦中的婚礼 147`、`6 轨 142`、`multitrack 117`（当前一律 100）。
另外 `STAFF_TOP_Y = 10` 对「高音谱表上方 8 个音级的加线」也偏紧（`梦中的婚礼` 高音谱表
内容上扩 90px，谱表原点 y=10 时最高内容已到 y≈0，贴住 SVG 上边缘），建议一并给足上留白。

## 3. 次因：源数据的连奏断音被拆成延音线碎片

`梦中的婚礼.mid` 右手轨的原始事件是成对的「note-on/off 紧邻」断音，例如：

```
beat 3.750 ON 79 / 3.985 off 79     ← 实际是同一个四分音符
beat 4.000 ON 79 / 4.235 off 79     ← 被切成两段 0.235 拍
beat 4.250 ON 81 / 4.485 off 81
beat 4.500 ON 81 / 4.735 off 81
```

0.235 拍在 1/16 网格上吸附成 0.25 拍，于是每个音变成「16 分 + 16 分（延音线）」。
量化器又因为下一段 start < 上一段 end 的判定把它们拆到不同声部，形成两条几乎同音的声部。

统计（`梦中的婚礼.mid`）：

- 音符事件 948 个，时值片段 1140 段（1.20 段/音符），190 个音符含多片段
- **相邻同音且首尾相接（本应合并为一个音）129 处**，占音符数 13.6%
- 带跨小节延音线的音符 95 个

它带来的观感问题正是设计文档 `20260905-score-key-estimate-and-beaming.draft1.md:33`
描述的「被拆成延音线粘连的八分+十六分，满屏连线」。

**修法**：量化阶段对「同谱表 + 同声部 + 同音名 + 前段结束 == 后段开始 + 断口 ≤ 网格步长」
的相邻事件做合并（用后者的结束时间延长前者），合并后再走原有的时值分解。
注意保留真正的重复音（例如同音反复的八分音符有明确断口 > 网格步长时不合并）。

> **已实现（2026-09-13）**：改为更严格的判据——「两段起止吸附到**同一网格点**」
> （即两段之间不存在任何网格点，量化后本就无法区分），不需要任何额外的断口阈值常数。
> 实现在 `quantize.ts` 的 `mergeLegatoFragments`，置于 `extendWithSustain` 之后。
> 实测：`梦中的婚礼.mid` 音符事件 948 → 884、跨声部同度重影符头 8 → 0；
> `demo.mid` 与 6 轨文件（无连奏断口）输出逐音符不变。剩余 2 处未合并的同音相邻对
> 断口 0.3~0.6 拍，是真正的同音反复音，符合预期。

## 4. 其它观察（非阻塞）

1. **空声部不画全小节休止符**：某声部在某小节没有事件时完全留白（小节里空着），
   记谱惯例应画居中的全小节休止符（`1r`）。
2. **系统左端只有一条竖线**：`StaveConnector` 用 `singleLeft`，草案
   `20260905-score-notation.draft1.md` §3 写的是「2 轨用 brace、>2 轨用 bracket」。
3. **小节线在系统内是独立 Stave 各自绘制的**：相邻两小节各有 1px 小节线，x 相差 4px，
   系统首小节还有「谱号区小节线 + 小节线」双重竖线。功能无误，观感略糙。
4. **偶发符头碰撞**：`梦中的婚礼.mid` 199 个符头位置里 4 处相邻间距 <8px（最小 0–1px），
   源于「4 小节/系统」在小屏下把密集 16 分音符压进 ~188px 的小节宽度。
5. **6 轨文件不是钢琴谱**：`pianokits-6track.mid` 有 3 个高音谱表音轨音域几乎相同
   （分别到 y=30/-5/-40），属于测试数据，不是渲染问题。

## 5. 已排除的误判（记录以免重复）

- **「多声部各自 format 导致同拍点错位」**：曾怀疑 `for (const v of voices) formatter.format([v], w)`
  会让两个声部独立分配间距。实测 `Formatter.createTickContexts` 建的是**全局共享的
  TickContext 列表**，各声部同 tick 的音符共享 `TickContext`；在真实应用中把
  `format` 改成 `joinVoices(voices).format(voices, w)` 后**渲染结果逐像素完全相同**
  （已回退该改动）。合成用例里出现的错位是因为两段测试代码构造的 voice 长度不同，
  不反映真实路径。
- **「谱面被 SVG 裁剪」——先误判为不存在，实际存在（见 §7）**：早期用 `getBBox()` 统计，
  越界数字既受 VexFlow 透明点击矩形（`opacity=0` 的 `<rect>`）干扰，`<text>` 元素在
  Bravura 字形下又返回 `height=160` 的假值，导致我先得出了「没有裁剪」的错误结论。
  改用元素的 `y` 属性直接核对后，才确认高音谱表最高音确实落在画布之外。

## 7. 后续修正：垂直布局（2026-09-13）

用户反馈「有些音符位置画错了」，经查是**垂直布局的三处硬错误**，均已修复（`src/ui/score-view.ts`）：

1. **高音被裁到画布之外**。原实现谱表上方固定只留 `STAFF_TOP_Y = 10px`，而本曲高音谱表
   最高音 C7 需要 11 个音级（55px）。实测该音符落在 `y = -5`，而 `viewBox` 从 0 开始
   → **符头与加线被裁掉**。现按 `5 × 上探音级数 + 留白` 计算顶部空间。
2. **相邻谱表内容重叠**。原 `STAFF_GAP = 100` 是固定值 → 净空恒为 60px。改为按音域计算：
   `间距 = 上谱表下探 + 下谱表上探 + 两侧留白`，下限仍保持设计约定的 6 个线间距。
3. **系统高度不足**。原 `系统高 = STAFF_TOP_Y + (n-1)×GAP + BOTTOM_PAD`，末谱表下方的
   下探内容会被切掉；现按末谱表下探量计算。

修后实测（`梦中的婚礼.mid`：高音谱表上线 100.5、低音谱表上线 220.5、间距 120px）：

| 指标             | 修前                       | 修后             |
| ---------------- | -------------------------- | ---------------- |
| 最高音位置       | y = -5（出画布，被裁）     | y = 55（画布内） |
| 相邻谱表内容重叠 | 17px（demo）/ 42px（6 轨） | 全部 ✅ 无重叠   |
| 谱表间内容净距   | 负值                       | 1~26px           |
| 内容越界系统数   | 6 / 6                      | 0 / 6            |

> **测量方法备注**：SVG `<text>` 的 `getBBox()` 在 Bravura 字形下会返回 `height=160`
> 的假值，不能用它判断越界。可靠做法是直接读元素的 `y` 属性，以及符干/符杠 `<path>`
> 的端点坐标。这一点曾让我得出过错误的「已裁剪/未裁剪」结论，记录以免重复。

## 8. 用户复核：第一个有音的小节（2026-09-13 续）

用户以 `.tmp/梦中的婚礼.mid` 为基准，要求核对「高音轨第一个有音的小节」（即旋律
`5 6 6 7 7 6 6 5 5 2 2 7 7 5 5 4`，F 大调唱名）。该小节在文件里是 **m1**（m0 是拾音小节），
源数据为 16 个八分音符：

```
G5 A5 A5 A#5 A#5 A5 A5 G5 G5 D5 D5 A#4 A#4 G4 G4 F5
（= F 大调  C  D  D  E  E  D  D  C  C  G  G  E  E  C  C  Bb，与用户所给序列完全对应，
   整曲比用户手上的谱子低一个纯四度，调号也不同：文件是 Bb 大调/G 小调）
```

核对中发现页面输出**丢音且音高错位**，最终定位到**两个独立 bug**：

### 8.1 拼写 bug：调号内的升降音被记成还原音（差半音）

`quantize.ts#spellPitch` 把「调号内自然音」与「调号内升降音」两个分支写在一起，
且命中后**只返回字母、不带升降号**：

```ts
// 旧实现
const altered = sharpSet.has(natural) ? natural + 1 : flatSet.has(natural) ? natural - 1 : natural
if (altered === pc) return { letter, accidental: '', octave } // ← 升降号丢失
```

后果（**实际音高错误**，不只是记号问题）：

| 调号                   | MIDI    | 旧输出                | 正确      |
| ---------------------- | ------- | --------------------- | --------- |
| Bb 大调/G 小调（2 降） | 70 / 82 | **B4 / B5**（还原音） | Bb4 / Bb5 |
| G 大调（1 升）         | 66      | **F4**（还原音）      | F#4       |

修法：拆成三步且顺序固定——① 调号内自然音（若该字母被调号升/降过则写 `n`）；
② 调号内升降音（**显式带 `#`/`b`**）；③ 与调号冲突的自然音 `n`；④ 其余黑键。
新增「全调号 × 全音高往返」测试（`spellPitch` 结果还原回 pitch class 必须等于原值）。

同时 `score-view.ts` 增补：已由调号覆盖的音不再重复画显式记号（标准记谱），
用 `measureAccidental()` 判断。

### 8.2 踏板延音污染时值（主因）

`extendWithSustain` 用 `soundingEndsUnderSustain` 把每个音延到踏板抬起。实测该曲
踏板一直踩着，于是 m1 的 16 个八分音符全部被拉长（如 `G5 4.0→5.75`），**造出源数据里
根本不存在的重叠**，后续 `clampNoteEndsToNextOnset` / `mergeLegatoFragments` 因此把序列
压成 13 个碎片、音高错位。

对照实验（同一份数据，仅关掉踏板延长）：

```
源      : 79,81,81,82,82,81,81,79,79,74,74,70,70,67,67,77  (16 个)
无踏板  : 79,81,81,82,82,81,81,79,79,74,74,70,70,67,67,77  ✅ 序列与位置完全正确
有踏板  : 79,81,81,82,79,81,82,81,79,74,70,67,77            ❌ 丢音 + 错位
```

修法：踏板延长**不得越过同轨的下一个起音**——演奏者已经弹下一个音了，记谱上该音
就到此为止。真正的持续低音（同轨后续起音都在它之后）不受影响。

### 8.3 复核结果

修后逐拍点核对（音高集合 + 位置，前 3 小节）：

| 小节/谱表         | 结果                                                                       |
| ----------------- | -------------------------------------------------------------------------- |
| m0 高音 / m0 低音 | 1/1、8/8 ✅                                                                |
| m1 高音 / m1 低音 | **16/16、8/8 ✅**                                                          |
| m2 高音 / m2 低音 | 8/8、6/6 ✅（页面多出的一个片段是 1.5 拍音按拍分解的延音线片段，正确行为） |

### 8.4 过程中的教训（重要）

1. **Vite 给模块 URL 加 `?t=<时间戳>`**：用裸路径 `import('/src/core/midi/quantize.ts')`
   会拿到**另一个模块实例**（可能是旧代码），导致连续多轮测量结果互相矛盾。
   凡在浏览器里探测应用内部状态，必须用 `score-view.ts` 源码里那个**带 `?t=` 的 URL**。
2. **`getBBox()` 不能用来判断裁剪**：`<text>` 在 Bravura 字形下返回 `height=160` 的假值；
   应直接读元素的 `y` 属性与 `<path>` 的端点坐标。
3. 一度把「和弦每符头一个附点」误判为「附点重复」——`Dot.buildAndAttach(all: true)`
   按 key 逐个挂载是正确行为。

## 9. 用户复核：符杠（连音）几乎全部丢失（2026-09-13 续）

用户反馈「音符几乎都单独画，希望还原乐谱中把相邻短音符连起来的画法」。实测确认属实：

| 小节 | 高音谱表音符 | 符杠组 | 独立符尾(flag) |
| ---- | ------------ | ------ | -------------- |
| m1   | 13           | **1**  | **11**         |
| m3   | 13           | **0**  | **12**         |

源数据里 m1 是 16 个等距八分音符（两两成对），正规谱就是按对连的。

### 根因：延音线片段被当成了符杠分组边界

`score-view.ts#buildVoice` 的分组循环：

```ts
// 旧实现
if (!this.isBeamable(pm.note) || pm.continuation) {
  flush()
  continue
} // ← 一律断开
```

`continuation` 指的是「延音线连接的后续片段」（piece index > 0）。而现实数据里，量化常常把
一个八分音符写成「八分 + 八分（延音线）」两段，于是**每个音的第二段都触发一次 flush**，
分组永远凑不满 2 个音，符杠全部被丢掉，只剩独立符尾。

修法：**延音线片段仍然参与符杠**，只有它落到别的拍组时才断开（那本来就是跨拍连线，
不该连符杠）：

```ts
// 新实现
if (!this.isBeamable(pm.note)) {
  flush()
  continue
}
const bi = beatIndex(pm.beatOffset)
if (group.length > 0 && bi !== groupBeat) flush()
group.push(pm.note)
groupBeat = bi
```

| 文件           | 符杠组     | 独立符尾   |
| -------------- | ---------- | ---------- |
| 梦中的婚礼.mid | 1 → **12** | 11 → **1** |
| demo.mid       | 4          | 4          |
| 6 轨.mid       | **24**     | **0**      |

### 顺带修掉：底部留白不足导致最低音被裁

`MIN_BOTTOM_PAD` 原为 10px，但五线**之下**的加线（下加一线，1 个音级）其符头下缘

`quantize.test.ts` 增加一组「符杠分组的输入形态」测试，钉住渲染端按拍分组的前提：

## 10. 用户复核：小节宽度与小节内容不匹配，音符挤出小节（2026-09-13 续）

用户反馈：m1 是 4/4、16 个八分音符，却和后面 3/4 的小节一样宽，音符画到了小节之外、
与下一小节重叠。

### 实测确认

```
m0 (4/4, 含谱号+拍号) 宽 286px   ← 凭空多出 ~90px 的记谱符号宽度
m1 (4/4, 16 个八分音符) 宽 196px  ← 每音仅 ~13px，而符头宽 12px
```

### 三处根因

1. **每行的小节数只看条数、不看内容密度**。原 `measuresPerSystem = (宽 - 48) / 210`，
   与每小节有多少音符无关；`perBeat` 又把可用宽**按小节数均分**，于是 3/8 的稀疏小节
   与 4/4 的密集小节占同样宽度，密集小节被压到符头相碰。

2. **计算「每行放几个小节」时漏算了谱号/调号/拍号的占宽**。行首小节要多画谱号+调号
   （约 90px）、拍号变化小节多约 95px，拟合时没算进去 → 估出的小节数偏多 →
   整行总宽超过画布。实测 `m0 = 120 + 90 = 275px`、`m1 = 185px`、`m2 = 234px`，
   合计 705px 却画在 520px 的画布上，最后一条小节线落在 **526.6 > 520**。

3. **内边距被重复扣了一次**：`width` 已经是 `el.clientWidth - SCROLL_PAD_X*2 - CARD_PAD_X*2`，
   拟合时又减了一次 `CARD_PAD_X*2`，可用宽被低估 48px。

### 修法

- `computeMeasureHeads()`：全曲预计算每小节「最密谱表」的符头数；小节下限宽度
  `max(MIN_MEASURE_PITCH, 符头数 × MIN_HEAD_SPACING)`，`MIN_HEAD_SPACING = 15px`。
- `measuresPerSystem` 改为**按各小节所需宽度累加**（含 `measurePrefixExtra()` 算出的
  谱号/调号/拍号占宽），而不是固定条数。
- 宽度分配改为**按小节拍数**（`perBeat × beatCount`），不再是每小节等宽。
- 去掉重复扣减的内边距。

### 修后实测

| 系统 | 画布宽 | 最后小节线 | 最右符头 | 越界  |
| ---- | ------ | ---------- | -------- | ----- |
| 0..5 | 520    | 516        | ≤507.6   | ✅ 无 |

四个测试文件（梦中的婚礼 / demo / 6 轨 / multitrack）全部无「符头挤过小节线」与
「超出画布」，符头间距 <8px 的相邻对由 12 处降到 6 处。

> 说明：该系统在分屏视图下只有 520px 宽，密集小节每音约 15px 已接近可读下限。
> 若要更宽松，可切到「仅乐谱」视图（画布更宽），或调大 `MIN_HEAD_SPACING`。

## 11. 用户复核：小节宽度应正比于**时值**（2026-09-13 续）

用户明确要求：**一个小节的宽度应与其时值成正比**——4/4 相当于全音符、3/4 是三个四分
音符、3/8 是其 3/8 倍。我先误做成「按符头数分配」（符头可代表任意时值，这是错的），
随后又因下限取得过大（`max(120, 符头数×15)`）把比例夹平，4/4、3/4、3/8 看起来一样宽。

### 正确的分配规则

```
音符区预算 = 画布宽 - 左留白 - Σ(谱号/调号/拍号占宽)
每小节音符区 = max(下限, 每拍宽度 × 该小节拍数)
```

关键是**先从预算里扣掉记谱符号占宽再按时值分**：否则行首小节（谱号+调号+拍号约 109px）
的份额大半被符号吃掉，它的音符区反被压扁——实测出现过行首 4/4 小节音符区 22px、
而同样 4/4 的次小节却有 104px 的反常情形。

### 换行（每行放几个小节）的依据

不能只看时值，还要看密度，否则一行会塞进过多小节把音符压到相碰。下限取两者较大值：

```
下限 = max(每拍下限 × 拍数, 符头数 × 每符头最小宽度) + 每拍余量 × 拍数
```

实测调参记录：

| 换行阈值       | 结果                                                 |
| -------------- | ---------------------------------------------------- |
| 28px/拍        | 一行塞 7 个小节，58 个符头里 36 处间距 <10px（相碰） |
| 70px/拍        | 一行只放 1 个小节（过度换行）                        |
| 26~46 + 密度项 | **一行 2 个小节，符头间距 ≥14px、无相碰、无越界** ✅ |

### 修后实测（`梦中的婚礼.mid`，分屏视图 520px 画布）

| 系统 | 小节            | 拍数      | 音符区宽度 | 宽/拍               |
| ---- | --------------- | --------- | ---------- | ------------------- |
| 0    | m0 4/4 / m1 4/4 | 4 / 4     | 相等       | 一致 ✅             |
| 1    | m2 3/4 / m3 7/8 | 3 / 3.5   | 比值 0.857 | 0.857 ✅（= 3/3.5） |
| 2    | m4 3/8 / m5 3/8 | 1.5 / 1.5 | 相等       | 一致 ✅             |

高音谱表符头最小间距 14~44px，`<10px` 的相邻对 **0 处**；四个测试文件均无越界。

> 另加一道**硬性兜底**：装配列宽后若总宽仍超出「画布 - 左留白 - 额外符号」，先按可压缩量
> 从有富余的小节里扣回（优先保下限），仍不够才整体等比缩小——保证绝不画出画布。
